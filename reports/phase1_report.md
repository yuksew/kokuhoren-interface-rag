## 2. Haiku 5.5 と Sonnet 5.5 の精度比較

### 検証条件
- 対象は13ページ（介護 共通編4・介護 サービス事業所編4・障害 サービス事業所編5）。内訳は単純な表3、セル結合5、改ページ分断6、必須対応表（行列）2（重複あり）。`config/pages.yaml` 参照。
- effort は両モデルとも `medium`。structured outputs（JSON スキーマ）を使った。`medium` は Haiku 5.5 の既定値だが、Sonnet 5.5 の既定値（`high`）より1段低い。条件はそろえてあるが「各モデルを既定値で動かした比較」ではない。Sonnet の続きのフラグや出力形式の誤りは、`high` にすると変わる可能性がある（未検証）。
- 同じページを **PDF 入力（1ページ切り出し）** と **PNG 入力（150dpi）** の両方で処理した。
- 正解との照合は、自動チェック、モデル間の食い違い、原本画像との突き合わせ（食い違ったセルはすべて、一致したセルは抜き取り）で行った。

### 最大の発見: PDF 入力では介護の桁数を落とす（モデルの差より大きい）
| | 介護 p80・p81・p84 の桁数（66行） |
|---|---|
| PDF 入力（Haiku・Sonnet とも） | **60行が null**。読めたのは2桁の「１０」「２０」だけ |
| PNG 入力（Haiku・Sonnet とも） | **66行すべて正解** |

- 原因: 介護の PDF では、全角1桁の桁数（「４」など）が、テキストレイヤ上で右隣の「内容」と同じテキスト片（`４ 交換情報識別番号を設定する`）にまとめて格納されている。PDF 入力ではモデルがこのテキストに引っ張られる。
- 障害の PDF は桁数が半角の別セルなので、PDF 入力でも問題なかった。
- PDF 入力では、必須対応表（介護 p110）の**縦書きの列見出しも読めなかった**（Sonnet は「判読不能」、Haiku は「見出し空欄1…」と出力）。PNG 入力では両モデルとも読めた。
- → **フェーズ2は PNG 入力を既定にする**（`transcribe.py` の既定値を変更済み）。

### 表の種類別の結果（PNG 入力）
| 表の種類 | ページ | Haiku | Sonnet |
|---|---|---|---|
| 単純な表 | 介護 p84、障害 p31 | 全項目一致。誤りは見つからず | 同左 |

PDF 入力では行列ページ（p90）の値も、**両モデルが別々の箇所で間違えた**（Haiku: 項番24〜26 で ○ を1つ落とした。Sonnet: 項番38〜40 で ○ を1列右にずらした）。

### まとめ
- **値の読み取り（項番・項目名・属性・桁数・内容・備考・必須記号）は、PNG 入力なら Haiku と Sonnet でほぼ差がない**。今回見つかった Haiku の誤りは、列見出し1件と文字の脱落4件で、どちらも小さい。
- Sonnet が勝ったのは「指示に忠実」な面: 縦結合のグループ名を落とさない、原文にない文を足さない。一方で、Sonnet も出力形式（空欄の列の省略）と続きのフラグでは間違えた。
- **続きのフラグはどちらのモデルも 82% で当てにならない**。フェーズ2では、項番の連続とページの並びからプログラムで判定すべき。
- 両モデルが同じ誤りをした場合、モデル間比較では検出できない。今回もテキストレイヤ照合で、「計」の脱落（部分文字列として一致してしまう）を拾えなかった。目視確認は欠かせない。

## 4. スキーマの修正と、フェーズ2への提案

### スキーマの修正点（`prompts/transcribe.schema.json`）と理由
| 修正 | 理由（実物で確認したこと） |
|---|---|
| `items` を `tables[]` の下に移した | 1ページに複数の表が載っている（共通編 p12 など） |
| `table_kind` を追加（record_layout / code_list / required_matrix / interface_list / other） | 共通編はコード一覧と項目説明で列の構成が違う。必須対応表は行列になっている |
| `name` を `name_path`（配列）に変えた | 「公費1 > 負担者番号」「合計情報 > 保険 > 請求額」のような縦結合の階層がある |
| `note` を `content`（内容）と `note`（備考）に分けた | どちらの分野も「内容」と「備考」が別の列になっている |
| `required` に加えて `required_by[]` を追加 | **介護の項目説明表には必須の列がない**（必須は別ページの「入力必須項目と様式の対応表」に ◎/○ で載っている）。障害は「※必須（識別番号毎）」が J121 / J131… の複数列に分かれている |
| `length` は整数にし、原文は `length_raw` に残す | 原本は全角数字。空欄の行もある（「データ」の行など） |
| `no_raw` を追加。項番の重複を許す | コード一覧で、1つの項番に複数の小項目がある（異動事由など） |
| `columns`・`title`・`footnotes`・`printed_page` を追加 | 備考の「※3」などの本文は表の下の注記にあり、次のページにまたがることもある（介護 p84→p85） |
| `domain` / `edition` / `volume` / `page` はモデルに書かせず、スクリプトが付ける | manifest から確実に分かるため |

### フェーズ2への提案
1. **入力は PNG（150dpi）を既定にする**。行列ページは 200dpi も試す価値がある。PDF のテキストレイヤは、モデルへの入力ではなく**答え合わせ**に使う。
2. **モデル構成**: Haiku と Sonnet の両方を Batch で全ページ処理する（両分野で約 $104）。両者の食い違いと、自動チェックで引っかかったセルだけを人が目視確認する。値が一致したセルは誤りの可能性が低い（今回の抜き取りでは全問正解）。予算を最小にしたい場合は、Haiku で全ページを処理し、引っかかったページだけ Sonnet で再処理する。
3. **後処理はプログラムで決める**:
   - 続きのフラグと、ページをまたぐ表の結合（項番の連続・同じ列見出し・ページ順から判定する）
   - 備考の「※n」と注記本文のひも付け（次ページの注記も含める）
   - 介護では、項目説明表（`record_layout`）と必須対応表（`required_matrix`）を「レコード名＋項番」で結合する
   - 必須対応表で空欄の列が省かれていたら、列名から位置を戻す
4. **検証を強める**: テキストレイヤ照合を、部分文字列の一致ではなく前後を含めた完全一致に強化する（「計」の脱落を拾うため）。項番の連続チェック、桁数の合計とレコード長の突き合わせも加える。
5. **費用を下げる**: 表のないページ（目次・図・空白）は、テキストレイヤに「項番」があるかどうかで事前に除外する。毎回同じシステムプロンプトとスキーマ（実測 4,960 トークン。入力の約6割）にはプロンプトキャッシュを使う。
6. **DB 化**: 文書（版・sha256）→ ページ → 表 → 項目 → 必須（列別）／コード値／注記、の階層で持つ。各行に出典（文書・ページ・画像）を残す。改定に追従するため、新旧対照表・修正履歴も取り込み、版間の差分を引けるようにする。
7. **RAG**: 検索の単位は「レコード（表）」と「項目（行）」にし、上位の情報名・レコード名・グループ名を文脈として付ける。項目名やコード値は完全一致検索、自然文は埋め込み検索、と組み合わせる。回答には仕様書のページ画像へのリンクを付ける。施行分が混在するので（判断に迷った点の4）、**サービス提供年月で版を選べる**ようにする。
8. **令和9年度改定への備え**: `fetch.py` を定期的に再実行し、sha256 の変化と WAM NET の新しい掲載を検知する。
9. 図の入ったセル（共通編 p35 の保険者番号の図など）は、言葉で説明させると原文どおりにならない。「図あり」の目印とページ画像への参照だけを残す方針にする。

- API キーはプロジェクト直下の `.env` から読み込む（既存の環境変数が優先）。`.env` は `.gitignore` に入れてある。
