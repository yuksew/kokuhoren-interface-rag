# フェーズ2 報告（1）: 検索

実施日: 2026-11-01　／　API 費用: **$0**（埋め込みはローカル GPU）

## 構成
| 部分 | 内容 |
|---|---|
| 埋め込み | `cl-nagoya/ruri-v3-310m`（Apache-2.0、日本語検索の JMTEB Retrieval 81.89）。RTX 3090 で 8,011 チャンクを 90 秒。モデルカードの指定どおり「検索クエリ: 」「検索文書: 」を付ける。`src/llm/embedding.py` の `EmbeddingClient` の裏に実装し、ほかのモデルに替えられる |
| チャンク | 行ごと 7,774 と表ごと 237。行のチャンクには、文書・版・節・表題・交換情報識別番号を見出しとして付ける（項目名のない行や表題のない表も見つかるように） |
| 全文検索 | SQLite FTS5 trigram。質問を助詞などで区切り、3文字以上の語の OR で引く |
| 番号の直接引き | 質問に既知の交換情報識別番号（J421、7131 など）があれば、インタフェース一覧のその番号の行を最優先にする |
| 融合 | 3つの結果を RRF（k=60）でまとめる。番号の直接引きは重み 2 |
| 絞り込み | 介護・障害（`--domain`）、交換情報識別番号（`--exchange`）は必ず守る条件 |

依存: torch などは依存グループ `rag` に分けた（`uv run --group rag ...`）。書き起こし側の `uv sync` には入らない。

## 評価（`eval/questions.yaml` 22問、`reports/retrieval_eval.md`）
質問は DB の内容を見て作った。種類は、項目名をそのまま含むもの 7、言い換え 10、番号で聞くもの 3、表単位 2。

| 方式 | hit@1 | hit@5 | hit@10 | MRR |
|---|--:|--:|--:|--:|
| 全文検索のみ | 0.41 | 0.59 | 0.64 | 0.47 |
| ベクトル検索のみ | 0.59 | 0.77 | 0.77 | 0.67 |
| ハイブリッド | 0.59 | 0.82 | 0.86 | 0.69 |
| **ハイブリッド＋番号の直接引き（採用）** | **0.73** | **0.91** | **0.95** | **0.81** |

- 言い換えにはベクトル検索が効いた（「利用者の生まれた日」→ 生年月日、「要介護度」→ 要介護状態区分コード）。全文検索だけでは 10 問中 5 問。
- 番号で聞く質問は、全文検索・ベクトル検索ともに外した（J421 を含むレコードの行が多すぎて、答えになるインタフェース一覧の行が埋もれる）。番号の直接引きで 3 問とも 1 位になった。
- 上位10件に入らなかったのは「男女の区別を入れる項目は？」（正解は性別コード）の1問。

注意
- 番号の直接引きは、評価で外れた3問を見てから加えた。22問は少ないので、ここでの数字は目安。質問を増やして確かめる必要がある。
- 正解は1つの行に決めているが、同じ項目が複数の表にある（受給者証番号など）。どれか1つが入れば正解とした。

# フェーズ2 報告（2）: 回答生成

API 費用: **$0.53**（評価・試行 115 回の合計。`out/answers/calls.jsonl` に1回ごとに記録）

## 構成（`src/ask.py`）
- 検索の上位12件を番号つきの「抜粋」として渡し、抜粋だけを根拠に答えさせる（`prompts/answer_system.md`）。
- 出力は構造化出力で `answer`（本文。事実に `[n]` を付ける）・`used`・`insufficient`。
- **出典はモデルに書かせず、引用された番号から DB で表示する**（文書・版・PDF ページ・印刷ページ・表題・項番）。存在しない番号の引用は検出して表示する。
- 「〇〇レコードの項目は？」のような質問（項目・構成・一覧など）では、該当する表の行一覧を丸ごと抜粋の先頭に入れる。

## 評価（22問、`reports/answer_eval.both_models.md`・`reports/answer_eval.haiku_final.md`）
| | Haiku 5.5 | Sonnet 5.5 |
|---|--:|--:|
| 期待する語をすべて含む（20問） | 20 | 20 |
| 正解の行を出典として引用（22問） | 22 | 22 |
| 存在しない抜粋番号の引用 | 0 | 0 |
| 1問あたりの費用 | $0.0007 | $0.011 |
| 応答（平均） | 1.9 秒 | 2.4 秒 |

初回は Haiku が 22問中12問で「抜粋だけでは答えられない」とし、期待する語も 19/20 だった。原因を見て次を直した。
- 介護の明細書のレコードは表題に「明細書」が無く、質問の「明細書」と結びつかなかった → チャンクの見出しに識別番号の**情報名**（「居宅介護（支援）給付費請求明細書情報」など）を加えた。
- 必須対応表の同名の行（「様式種別番号」が版ごとに26表）が、項目の定義の行を押し出した → 必須対応表の行の重みを 0.5 に下げた（質問に「必須」「様式ごと」などがあるときは下げない）。
- 全文検索が「設定する」のようなどの行にもある語で引いていた → 行の3%超に出る語は使わない。
- 「答えられない」の基準を、質問の中心に答えられないときだけに絞った。
- 評価の正解のうち2問が狭すぎた・広すぎたので直した（「男女の区別」は共通編のコード一覧の性別コードも正解。「様式種別番号の形式」は必須対応表の行を正解から外した）。

この結果、検索は hit@5 0.95・hit@10 1.00・MRR 0.84 になった（`reports/retrieval_eval.md`）。

## 回答を読んで分かったこと（自動の指標では捕まらない誤り）
- **Haiku は細部を取り違えることがある。** 「様式種別番号」の属性を「英数」と書いた（正しくはコード値）。「特定入所者介護サービス費等の保険請求額の合計」で、先に別の項目（保険請求額 項番16）を挙げた。
- **Sonnet にも混同がある。** 「返戻等一覧表情報の識別番号」で、地域生活支援事業の L721 をサービス事業所等向けとして挙げた。
- そのため、**既定のモデルは Sonnet にした**（`--model` で替えられる）。1問 $0.011 なので、人が使う範囲では費用は問題にならない。大量の自動処理には Haiku を使い分けるとよい。

## 残る課題
- 評価の22問は私が DB を見て作ったもの。実際の利用者の質問で評価し直す必要がある。
- 同じ項目名が介護・障害、障害者（J）・障害児（K）・地域生活支援（L）にあると、どれの話か混ざることがある。画面では介護・障害の選択に加えて、対象（J/K/L）も選べるようにするとよい。
- 表全体を渡す質問は入力が増える（最大 1.3万トークン程度）。
